# L4 视觉检查详细规范

L4 E2E 的强制项。每条都来自真实踩坑案例——DOM 数值全绿 ≠ 视觉无问题，两者互补、缺一不可。主流程只在步骤 4/5 引用本文，执行 L4 前必读。

## 1. 截图检查（每页必截必看）

截图不只是存证，更是主动的**视觉检查手段**：每个核心页面（桌面 + 移动视口）`page.screenshot()` 后必须用 `vision_analyze` / 人工检查截图本身——看布局比例、裁切、遮挡、错位、溢出，不能只依赖 DOM 数值检测。

- 实测案例：admin dashboard 热门榜表格被裁切、卡片压成 1/3 宽，程序检测 `scrollWidth` 全绿（无页面级溢出）完全没发现，是视觉看截图才暴露的。
- 截图路径留档，写进报告缺陷条目。

## 2. 移动端视口（强制）

只测桌面视口会漏掉响应式缺陷。用 playwright/CDP 模拟 **390×844（iPhone）** 逐页检查：

- `document.documentElement.scrollWidth > window.innerWidth` 即为溢出。
- 表格/操作列/按钮必须在视口内可见可点。
- 移动端专项放 L4 最后一段，报告报 `mobile-layout` 通过率。
- 实测案例：收藏页表格 `scroll={{x:820}}` 在 390px 视口下操作列完全被遮挡、横向滚动无效，用户反馈「手机上布局被遮挡」后才暴露。

## 3. 布局比例检查（不只看溢出）

无溢出 ≠ 布局正确。用 playwright 读取关键元素 `getComputedStyle(el).gridColumn` / `getBoundingClientRect().width` 与设计意图比对（如 grid 列占比、表格容器 vs 表格内容宽度）。

- 实测案例：admin dashboard 全部图表卡被 CSS 选择器优先级 bug 压成 1/3 宽——`.dash-grid > .panel{span 4}` 特异性 0,2,0 覆盖 `.chart-lg{span 8}` 0,1,0，运营趋势该占 2/3 只占 1/3，热门榜表格被塞进窄容器内部横向滚动。
- 排查 CSS 覆盖时优先怀疑特异性（类数多者胜）；修复用 `.dash-grid > .panel.chart-lg` 提特异性的写法，不要改样式顺序碰运气。

## 4. AI 助手生成文本四方核对（L1/L4）

AI 助手（LLM 工具链）返回的**文本内容**也要与真实数据核对——测试只验 API/DB/前端三方一致会漏掉 LLM 生成文本这第四方。

- 实测案例：AI 回答「收藏列表全部标记为看过」，实际数据库 type=3 全是在看——prompt 缺收藏类型映射（1=想看 2=看过 3=在看）导致 LLM 猜错。
- 方法：用测试账号问 AI「我的收藏列表」等自然语言问题，把回答中的状态/数量/评分与接口数据逐项核对，不一致记 FAIL。
- 推论：prompt 中与数据语义相关的映射说明缺失，本身就是一个可测缺陷（记 P1）。

## 5. 全视口回归

用户修复后下一轮测试用同视口同页面重截；进入步骤 7 前全视口回归（**1280 / 768 / 390**）无溢出。

## 6. 断言先确认组件渲染形式（实测教训）

写/改页面断言前，先确认该组件**用文本还是图形（颜色/图标/条）表达状态**，别按旧实现断言：

- 实测案例（2026-08-11-r2）：导入状态面板改为 BarList 渲染（颜色区分状态，无「成功/失败」文本），旧断言查找「FAILED/成功/失败」文本误报 → 改为断言「共 N 条记录」+ 内容条存在 + console 0 错误。

## 7. 报告定稿自查

报告/计划提交给用户前，全篇 grep `可能|也许|应该|大概|推测|猜测`：命中仅允许出现在「待核实清单 / 未确认原因」语境，其余即违反「铁律：禁止猜测」，改写后再交付。

## 截图检查分工（防误解）

截图检查归 Hermes（vision_analyze 看截图本身）。发现布局缺陷后，把具体描述（元素/期望 vs 实际/截图路径）写进报告缺陷清单交接用户；修复由用户或其他流程执行。前端布局错误的检测能力上限 = Hermes 视觉检查的质量。
