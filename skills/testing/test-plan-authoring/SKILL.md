# Test Plan Authoring（测试计划编写）

将测试计划写成“交给 AI 可直接执行的任务规格”：每个用例可追踪、可重放、可判定，测试数据可恢复，结果可统计，计划与报告严格分离。

## 0. 铁律

1. **先盘点，后写数。** 测试文件数量、用例数量、分层定义必须来自当前代码的实时盘点，禁止沿用旧计划、旧报告或历史经验中的数字。
2. **版本锚定。** 每个计划必须记录被测 commit、工作区状态、构建产物指纹、运行进程指纹；不知道在测什么版本的报告没有价值。
3. **数据可还原。** 执行前记录基线，执行后必须清理/恢复；没有清理步骤的用例不允许写进计划。
4. **数字可推导。** 报告里的总数、PASS/FAIL/SKIP/LIMITED、未执行数必须能从计划用例 ID 逐条对账出来。
5. **未执行不是 LIMITED。** “没测”和“测了但环境受限”是两种状态；LIMITED 必须有已观察到的响应/现象和补测条件。

## 1. 核心原则（六条）

1. **用例可追踪**：每个用例对应需求/验收项，附需求覆盖矩阵。
2. **用例可重放**：任何人拿到计划都能按相同顺序、相同数据、相同命令执行。
3. **预期可判定**：每条期望至少包含 HTTP 状态码或 UI 状态，以及至少一个可判定的字段/数值。
4. **数据可恢复**：执行前记录基线，执行后清理/恢复；破坏性用例使用隔离账号。
5. **结果可统计**：用例总数、PASS/FAIL/SKIP/LIMITED/未执行数在计划中可直接汇总。
6. **计划与报告分离**：计划定义做法与判定标准；报告只记录执行结果，引用计划中的用例 ID。

## 2. 标准结构

### 0. 元信息
- 计划版本、生效日期、适用项目/分支。
- 被测系统版本：commit、工作区 dirty 清单、前后端版本、数据库 schema 版本。
- 执行人/执行器、预计时长。

### 1. 目标与范围
- 可验证的验收标准，例如“连续 5 次错误密码后第 6 次必须拒绝”。
- 纳入范围：明确列出模块。
- 不纳入范围：明确列出，避免误测。
- 需求覆盖矩阵：需求/验收项 → 用例 ID。

### 2. 环境与准入条件
- 服务清单：进程、端口、健康检查 URL、期望状态。
- 依赖清单：MySQL/Redis/MinIO/外部模型服务等，附 `docker ps` / `curl` 探活命令。
- 测试数据基线：账号、fixture、当前数据量。
- 准入标准：所有 readiness 检查通过才能执行；不通过进入环境问题处理流程。
- **版本指纹**：记录 commit SHA、构建时间、jar/class mtime、进程启动时间，确保“源码变了但测的是旧产物”这种问题能在执行前暴露。

### 3. 测试数据管理
- fixture 表：数据 / 用途 / 是否破坏性 / 准备命令 / 清理命令。
- 破坏性用例必须使用隔离账号，例如 `e2e_lock_test`。
- 每个用例注明：前置数据、执行后预期、清理动作。
- **清理脚本必须真实存在**。计划里不得引用 `scripts/test-fixtures/` 下不存在的文件；写计划前先盘点脚本目录。
- **后置门禁（强制）**：执行结束后必须按顺序执行：重放 seed → 清 Redis 测试键 → 删除 MinIO/对象存储测试对象 → 对比最终计数。任何残留都必须写进报告，不允许静默忽略。

### 4. 用例清单
每个用例使用以下字段：

| 字段 | 说明 |
|---|---|
| ID | 唯一编号，例如 `API-AUTH-003` |
| 优先级 | P0/P1/P2 |
| 前置条件 | 账号、数据、服务状态 |
| 步骤 | 可执行的编号步骤，含 URL、请求体、操作路径 |
| 期望结果 | 状态码、响应结构、关键字段、UI 状态 |
| 清理 | 恢复数据、退出登录、删除测试记录 |
| 证据 | 截图、日志、命令输出 |
| 状态 | 执行后填写：PASS/FAIL/SKIP/LIMITED/未执行 |

### 5. 执行顺序与缺陷流程
- 顺序：环境检查 → 版本指纹核对 → 单元层 → 接口层 → E2E。
- 缺陷处理：记录复现步骤 → 判定严重度 → 按约定决定是否本地修复 → 修复后执行该用例及关联回归。
- 是否自动修复由任务指令决定，计划不默认改写代码。

### 6. 风险与退出标准
- 风险表：环境、数据、外部依赖、长连接。
- 退出标准：无未处理 P0/P1 且有明确处置结论，覆盖率达到约定值。
- 阻断标准：核心依赖不可用且 30 分钟无法恢复 → 停止该层。

### 7. 报告模板
- 执行环境：版本、时间、服务状态、数据基线、版本指纹。
- 结果汇总：分层四态计数、未执行数、通过率、覆盖数、耗时。
- 失败明细：用例 ID、期望、实际、复现步骤、严重度。
- 受限明细：受限项、原因、已观察现象、补测条件。
- 未执行明细：未执行项、原因、计划补测轮次。
- 上线建议：按 P0/P1 阻断结论，给出明确建议。

## 3. 用例编号规范

`{层}-{模块}-{序号}`，例如 `API-AUTH-003`、`UNIT-JAVA-007`、`E2E-ADMIN-001`、`L2-FRONTEND-002`。

编号发布后不可复用；语义变化时生成新 ID 并记录变更。计划直接给出每层与总用例数。

## 4. 状态四态与统计口径

| 状态 | 定义 |
|---|---|
| PASS | 已执行，实际结果完全满足期望 |
| FAIL | 已执行，实际结果不满足期望，属于缺陷或断言失败 |
| SKIP | 已进入执行流程，因明确前置条件不满足主动跳过 |
| LIMITED | 已尝试执行，因环境/外部依赖/工具限制无法得到有效结论，必须附已观察现象和补测条件 |
| 未执行 | 计划内但没有进入执行，单独计数，不占四态 |

**统计口径（所有计划/报告强制一致）：**

```text
plan_total     = 计划用例 ID 总数
executed       = PASS + FAIL + SKIP + LIMITED（已执行）
not_executed   = plan_total - executed
通过率          = PASS / (PASS + FAIL)
实际覆盖率      = executed / plan_total
规范操作覆盖     = 已覆盖操作数 / 规范操作总数
```

报告中必须同时给出通过率与实际覆盖率。禁止用“PASS/(PASS+FAIL)”冒充总覆盖；未执行项越多，结论置信度越低。

## 5. AI 执行者指令（§0）

计划交给 AI 执行时，顶部必须包含执行说明：

1. 端点以实际代码为准：执行前 `rg "Mapping("` / 搜索 controller，核对真实端点、参数绑定方式、DTO 字段。
2. 严格按层串行执行；同层内按计划顺序。
3. 失败二分：环境问题 → LIMITED（附补测条件），代码缺陷 → 记录并本地修复，修复后回归。
4. 测试账号预置，禁止中途注册新账号（防限流污染）。
5. 安全：报告不写 token、密钥、密码。
6. 输出报告路径 + 是否自动提交，以任务指令为准（默认不自动提交，留人工 review）。
7. **执行前先做版本指纹校验**：确认运行进程/构建产物与计划声明的 commit 一致；不一致立即停止并标记 BLOCKED。
8. **执行后必须跑后置清理门禁**，未清理不允许出“上线建议”。

## 6. 写文档前必做代码调研

- **测试文件盘点（每次必做）**：

```bash
# Java 单测
rg --files backend -g '*.java' | rg '/src/test/'
# Python 测试
rg --files backend -g 'test_*.py' -g '*_test.py' -g 'tests/' -g '!**/.venv/**'
```

  记录实际文件数并写进计划。**测试文件数为 0 就写 0**，不能写“35”或“28”，更不能把 `mvn test` 的空跑当作覆盖。

- **端点必须核对真实 controller**：旧文档可能与代码漂移。先 `rg` 真实端点，再写用例。
- **参数绑定方式必须核对签名**：`@RequestParam`（query）vs `@RequestBody`（JSON）写错会得到误导性错误；写 L3 脚本前先确认 controller 方法签名。
- **核对响应包装结构**：如 `Result<T>{code,message,data}`、`PageResult` 是 `content` 还是 `records`、`total` 字段名。写断言前用 curl 看原始响应。
- **OpenAPI 与代码一致性检查**：写计划时对比 `openapi.yaml` 操作数 vs controller 实际端点数，不一致先修文档或注明漂移，契约测试不基于已漂移的规范。
- **构建产物检查**：`mvn test` stdout 不可靠，用 surefire 报告聚合；增量构建可能跑旧 class，必须 `mvn clean test` 或核对 `.class`/jar 的 mtime。

## 7. 测试数据管理门禁

### 写计划时
- 盘点 `scripts/test-fixtures/`，所有 seed/reset/cleanup 脚本必须真实存在；不存在就把“补脚本”列为计划前置任务。
- 每个破坏性用例都有隔离账号和清理步骤。
- 记录基线：表计数、文件数量、Redis 键、MinIO 对象清单。

### 执行后（强制门禁）
```text
1. 重放 seed / 恢复基线数据
2. 删除测试期间创建的 Redis 键
3. 删除测试上传的 MinIO/对象存储对象
4. 校验最终计数 == 基线计数（允许的漂移需在报告中注明）
5. 任何残留写入报告“数据残留”章节
```

失败路径也必须清理：例如密码修改测试失败后，账号可能已经不可登录；必须用 seed 或管理员通道恢复，而不是“这次没走到那一步就不管”。

## 8. 契约测试脚本要求

1. **产物路径参数化**：结果文件至少包含日期和 commit 短 SHA，如 `api-contract-results-2026-08-15-8d57c51.json`；禁止硬编码日期导致历史结果被覆盖。
2. **断言必须是强断言**：不能只查 `isinstance(d, list)`。至少包含：
   - HTTP 状态码、`code`、`message`；
   - `data` 存在性及关键字段类型；
   - 列表长度 / `total`；
   - 排序规则、分页边界；
   - 关键字段值与 DB 查询结果三方一致。
3. **请求会话**：设置超时、连接重试（仅对瞬时网络错误），并记录每次请求的耗时。
4. **环境探活**：被测服务不可用时标记“未执行”或“LIMITED（附探活响应）”，不能静默 PASS。
5. **失败定位**：脚本解析失败 ≠ 产品缺陷；先 curl 原始响应确认结构，再定性。
6. **SSE/长连接**：按 `data: {json}` 逐行解析，`type=answer` 块拼全文核对；禁止 grep 固定字段名。
7. **测试后状态校验**：契约脚本结束必须输出最终数据状态；能自动清理的用例用 `finally` 清理，并在报告中声明。

## 9. 已知缺陷类（写入计划的回归项）

- 统计卡片用窗口数据过滤导致数字偏小：后端必须返回 DB 全量聚合，前端不过滤。
- 卡片数字语义以用户最终说法为准；实现前用一句话复述“这个数字 = 哪张表的哪个 count”。
- VO 字段改名要同步：VO.java + Service 取值 + 单测断言 + `types/api.ts` + 页面组件 + mock 数据 + openapi.yaml，漏任何一个都可能被类型检查或契约测试抓到。
- MyBatis 别名 vs VO 驼峰映射：聚合字段需要 `AS xxx_count`，且 `ORDER BY/HAVING/GROUP BY` 要同步改。
- 状态面板只有颜色没有文本时，断言“FAILED/成功/失败”文本必然失败；改断言“共 N 条记录 / 内容条存在”。
- 登录按钮文案随端变化：选择器按 `button[type=submit]` → `has-text("登 录")` → `has-text("进入控制台")` 依次 fallback。
- 页面路由、字段名、inner_text 换行、按钮空格等细节以实测为准，先 curl / 截图确认再写断言。
- 限流语义先读代码再定预期：例如“第 6 次起拒绝”≠“第 5 次”，测试完必须清 Redis 解锁键。
- 跨层用例的数据副作用：L3 改了收藏状态后，L4 断言必须用 DB 动态比对，不能按 seed 硬编码。
- 浏览器测试：`networkidle` 在轮询/SSE 页面永不触发，统一用 `domcontentloaded` + 固定等待。
- 截图检查是强制手段：DOM 数值全绿不代表视觉无问题，每页截图必须人工/视觉模型检查裁切、遮挡、错位。

## 11. 交付与版本管理

- 提交遵循项目 `.gitmessage` 规范（如 `feat(scope): 中文描述`）。
- 测试机执行的修复与测试报告默认不提交，留在工作区等人工 review（用户明确要求时除外）。
- 下一轮计划必须把工作区遗留改动列入待提交清单。
- 上线建议必须附：版本指纹、分层汇总、缺陷清单、清理门禁结果、回滚条件。
