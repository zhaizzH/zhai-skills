# 多版本对照项目的目录规范

## 这个技能解决什么

一个既有项目用 N 种风格各改一遍、横向对比，产物会散成一堆目录。这个技能只回答一个问题：

> **第 N 个版本的产物放在哪、叫什么名字？**

**不管代码怎么写。** 抽象方式、模块拆分、命名细节、依赖选择各版自定 —— 那正是风格差异的来源。
规范只保证一件事：**不同版本的同名文件能直接对照**，`diff v01/src/x v02/src/x` 有锚点。

## 唯一真源

目录规范的真源是**一个文件**：

```
poly-version-generator/scripts/audit_layout.py
```

里面的 `SNAPSHOT` `Profile` 就是规范本身。本文件和各区 `项目总结.md` 的第一节
都是它的派生 —— **不要手抄一份树到别处**。

配套参考（按需查阅，不必通读）：

| 文件 | 何时看 |
|---|---|
| [`references/rules.md`](references/rules.md) | 想知道硬性规则的完整清单与理由 |
| [`references/troubleshooting.md`](references/troubleshooting.md) | 审计报错时对照处理 |

## 版本是什么

每版是既有项目的**完整源码快照**，只锁 `src/`：里面原有几个包、几个 `.java`、
怎么分包，一律照抄原项目、审计不看。

```
poly-<实验>/
├── 项目总结.md         区根唯一一份文档
├── v01/
│   └── src/            该分支的完整源码快照
├── v02/
│   └── src/
└── …
```

**版本区不收录 IDE 文件**（`.iml`/`.iws`/`.ipr`/`.idea/`）—— 它们是 IDE 本机状态、
可重新生成，不是版本产物。

## 配置行：区文档里的入口

区文档里的 `` - `键` = `值` `` 行有两类，**形状即语义**：

| 形状 | 含义 | 例 |
|---|---|---|
| `` `<Xxx>` ``（带尖括号） | 占位符映射：把规范里的占位符指到本实验的实际名 | `` - `<Xxx>` = `SingletonDemo` `` |
| 其它标识符 | **配置覆盖**（下表，全部可选） | `` - `required` = `src/` `` |

| 配置键 | 缺省 | 作用 |
|---|---|---|
| `entry` | 空 | 入口文件模式，一般不用 |
| `required` | `src/` | 版本根必需项，**写了就只查列出的这些** |

**不写任何配置行 = 只查 `src/`** —— 既有版本区无需迁移。

清单键可写在一个反引号对里（逗号分隔）或每值一对反引号，两种写法等价。

## 三种用法

### 1. 建新版本区

1. 在仓库里建版本区目录 `poly-<实验>/`（如 `poly-singleton/`）。
2. 建 `项目总结.md`，先写需要的配置行（见上一节）。
3. 生成规范节，替掉占位内容：

   ```bash
   A=poly-version-generator/scripts/audit_layout.py
   python $A <版本区> --emit-spec -o spec.md
   ```

   生成物自带首尾边界（首行 `<!-- 本节由 poly-version-generator/scripts/audit_layout.py --emit-spec 生成，勿手改 -->`、末行
   `<!-- 本节结束 -->`）。**只替换「一、目录与文件树」这一节**：首行标记到末行
   标记整段换掉，其余各节原样保留。

   ```bash
   # 直接就地替换（推荐）：读回 项目总结.md，把标记之间那段换掉，其余不动
   python $A <版本区> --emit-spec --apply-spec -o <版本区>/项目总结.md
   ```

   `--apply-spec` 找不到标记就报错**不写**（不猜边界）；首次建区还没有那一节时，
   先用 `-o spec.md` 生成到临时文件、手工贴进去。
4. 写完 `项目总结.md` 的其余三节（见下）。

### 2. 只留一份文档：`项目总结.md`

整个版本区只有这一份 md，版本目录里一份不留。四块内容与来源
（迁移前的四份文档已并入本文件，不要再新建）：

| 块 | 原属 | 记什么 |
|---|---|---|
| 一、目录与文件树 | `CONTRACT.md` 第一节 | `--emit-spec` 生成，勿手改 |
| 二、版本→风格映射 + 各版状态 | `PLAN.md` | 要做几版、各是什么、做到哪一步 |
| 三、各版实际产出与取舍 | 每版 `MANIFEST.md` | 这版实际有什么、为什么多/少一个文件、校验记录 |
| 四、横向结论 | `REPORT.md` | 比下来谁赢在哪儿 |

少写文档 ≠ 少记信息。最容易丢的是「这版为什么多/少一个文件」—— `diff` 只显示
两版差在哪，不说明那是有意为之还是漏了；解释必须落在第三块里。

**写第三块时用增量口径**：每版只写与基线（v01）不同的地方与原因，不重复规范节已
声明的东西。同一件事（如某版的取舍）只在一处详写，其余处引指针；超纲例外这类跨
版本事实单列一张表，正文不重复叙述。

### 3. 审计布局

每批版本做完后跑一遍：

```bash
A=poly-version-generator/scripts/audit_layout.py
python $A <版本区>
python $A <版本区> --only v03             # 只审一个
python $A <版本区> --profile source-snapshot  # 区文档没写 profile 行时
```

退出码 0 = 全 PASS，1 = 有版本 FAIL。输出是逐版本的 PASS/FAIL 表，
样例见 [`references/troubleshooting.md`](references/troubleshooting.md) 开头。

- **区根文档**单独一块：`CONTRACT.md`/`PLAN.md`/`REPORT.md` 只要还在就会被报 ——
  判据是**文件存在**，不是内容为空。
- 审计只查「放哪、叫什么」，**不看文件内容与功能实现**。

## 核心约束

通则：**区根只有一份 `项目总结.md`，版本目录里不放任何 md**；版本根只该有 `src/`。
完整硬性规则见 [`references/rules.md`](references/rules.md)。

**本技能不带模板**：源码快照由各区自行导出，技能只当 `src/` 是个约定名去审计。

## 与实验报告技能的分工

本技能**只管道内**：版本区 `poly-<实验>/`、其下的 `vNN/`。
仓库根那些顶层目录（如课程提交目录）归**报告类技能**管，本技能不碰。
