# 硬性规则与忽略清单

> 本文件是 `SKILL.md` 的参考附录，按需查阅。规则本体在
> `scripts/audit_layout.py` 的 `Profile` 定义里 —— 本文件是它的**说明**，
> 两者不符时以脚本为准，并重跑 `--emit-spec` 覆盖区文档的规范节。

## 硬性规则（速查）

完整的树与逐条理由见 `项目总结.md` 第一节（由 `--emit-spec` 生成）。要点：

| 规则 | 原因 |
|------|------|
| 区根只有一份 `项目总结.md`，版本目录里**不放任何 md** | 四份 md 并存时改一处漏一处；旧文档会让人不知道哪份是真的 |
| 版本根**只有 `src/`** | 本 profile 只锁 `src/`；别的顶层文件/目录都不是版本产物 |
| **`src/` 内部结构自定** | 几个子目录、几个源文件、怎么分包一律由各版自定，审计不看 |
| `src/` 必须存在 | 它是唯一的必需项；缺了整个版本没有交付内容 |
| 各版 `src/` 整体结构应一致 | 跨版本 `diff` 才有锚点（这一条靠人保证，脚本只查 `src/` 在不在） |
| 入口文件存在性 | 只有区文档写了 `entry` 才检查；不写则不锁具体入口名，因为「整体结构一致」由人保证 |
| **交付源码里不得出现版本号/风格名/设计模式名/「契约」**（有机器检查，`java_checks` = `off` 可关） | 每份要能当独立的人写的东西交出去；出现这些词＝暴露「同一批人的多版本实验」 |
| **文件头不得抄「编译 / 运行」命令行**（有机器检查，`java_checks` = `off` 可关） | 编译运行方法属于交付说明；夹在注释里像 README 摘抄。行内提到 `javac` 不算 |
| **每个版本独立编译、独立 out、独立工作目录**（有机器检查，`code_checks` = `off` 可关） | 多版复用同名包与同名 `Main` 在布局上合法（`src/` 内部不受约束），但编进同一个 `out/` 或从同一个 classpath 运行就会挑错 `Main.class`、拉错兄弟版本的 `model.Player` |
| **代码检查没全 PASS 不得进入下一步** | 编译不通过、同类名冲突、out 被污染时写报告 / 打包 / 横向对比都是白做 |
| 不收 IDE 文件（`.iml`/`.iws`/`.ipr`/`.idea/`） | 那是 IDE 本机状态，可重新生成，不是交给老师的东西；仓库根的 `.idea/`、`.iml` 同理不归本技能管 |

**已取消的约束**（不要再照旧文档执行）：
- 单文件约束 —— 代码可以是多个文件、多个包。
- 行数上限 —— 无 `max_lines` 配置键。
- `提交/` 提交包 —— 无 `submit` 配置键，无 `_pack.py` 约定，审计不检查。
- 报告 docx / `report/` / `test/` / `README.txt` 的布局约定 —— 本 profile 不管这些。

## 审计不看的东西

编译产物与临时文件一律忽略，**所以 `javac` 跑过之后再审计也能 PASS**：
`*.class`/`*.jar`、`bin/`/`out/`/`target/`/`build/`、`__pycache__/`/`.venv/`、
`截图/`（截图工具的产出）、`~$*`/`.*~`。
`check_code.txt` 也是忽略项 —— 它是 `check_code.py` 的检查报告，不是交付产物。

清单在脚本的 `IGNORE_DIRS` / `IGNORE_GLOBS` 里。**增删时同步看一眼仓库根 `.gitignore`** ——
两处覆盖的类别应当一致，否则会出现「git 不管、审计也放行」或反过来「git 不管、审计却报错」的错位。
