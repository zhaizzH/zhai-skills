# 排障

> 「现象 → 原因与处理」表。多数条目由审计器的报错文案直接触发。

## 审计输出长什么样

```
审计 poly-singleton/ —— 共 5 个版本
profile：poly-version（同一目标整体结构相同、内部细节各异的若干实现，故只锁 `src/`。）
映射：区文档里没有映射行（本 profile 不靠映射行定位文件）

√ v01  PASS
× v02  FAIL
    - 版本根下多出目录 out/（不在本 profile 的规范内；弹性区只有 src）

× 区根文档  FAIL
    - 区根还有 PLAN.md —— 现在只留一份 项目总结.md，把 PLAN.md 的内容并进去后删除该文件

结果：1/3 PASS，2 处有待修正
```

## 常见问题

| 现象 | 原因与处理 |
|------|-----------|
| 审计报「区根还有 `CONTRACT.md`」 | 四份 md 已合并成 `项目总结.md` 一份。把内容并进对应四块后删掉旧文件 |
| 审计报「版本目录里不该有 `MANIFEST.md`」 | 每版不再各带一份文档，「本版有什么、本版取舍、校验记录」并进 `项目总结.md` 第三块 |
| 审计结果和预期差很多 | **profile 认错了**。本技能只有一个 profile `poly-version`；检查 `项目总结.md` 里有没有 `` - `profile` = `poly-version` ``，或本次加 `--profile poly-version` |
| 审计提示「`需求描述` 映射行已失效」 | `.iml` 不再进版本区。删掉区文档里那行 `` - `<模块>` = `PlanWar` `` 即可 —— 它现在什么都不指向 |
| 审计报「版本根下多出目录 `out/`」 | 构建产物不算数。删掉，或把探针/构建输出放到仓库根的 `out/`（本技能不碰仓库根） |
| 审计报「多出顶层文件 xxx」 | 该文件不在 `Profile.spec` 里。删掉它，或它确实该在版本根 → 在区文档加 `required` 声明 |
| 审计报「缺必需目录 `src`」 | 版本根必须只有 `src/`，且它得存在。把源码放进 `vNN/src/` |
| 审计报「交付源码里出现了 …」 | 源码里有版本号/风格名/模式名/「契约」，或文件头抄了编译运行命令。改掉这些词；若该区确实不需要这道检查，加 `` - `java_checks` = `off` `` |
| 想给某版单独跑一遍看看（要 IDE 能编译） | 别往 `vNN/` 里放 `.iml`。用原项目的模块，或在 IDE 里把该版 `src/` 手动标成 source root —— 版本区审计不看你这么做，但目录里也不该留下痕迹 |
| 改完树，`项目总结.md` 与审计结果不一致 | 树只该在脚本里改一次，然后重跑 `--emit-spec` 覆盖第一节。不要手改生成节 |
| 审计输出里的标记显示成 `?`（如 `? v01 FAIL`） | GBK 控制台编不出 `⚠`/`√`。审计器已把「异常退出」降级为「个别字符替换」，**结论照样是完整跑完的**；想让标记完整显示就加 `PYTHONIOENCODING=utf-8`，或直接 `-o` 写文件 |
| 区文档里写了 `profile` 行但被命令行覆盖 | 命令行 `--profile` 优先，审计器会打印一句提示。删掉命令行参数即按文档走 |
